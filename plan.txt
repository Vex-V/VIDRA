FALCONVAR IMPROVEMENT PLAN
==========================
This document describes every change to make, in implementation order.
Each section is a self-contained unit of work.


1. DUAL-MODE COMPONENT INTERFACE (accept objects OR resolve from disk)
=====================================================================

Goal: every Level 1 component should accept typed input objects as an
alternative to resolving them from disk by video_id. Pipeline users keep
passing ids. Standalone users pass data directly, no filesystem needed.

The existing run(video_id, ...) signatures stay unchanged. Add a second
entry point to each component that accepts the typed objects the component
would otherwise load from disk.

Pattern:

    # Existing (unchanged):
    boundaries.run(vid, "scene", chunk_s=20.0)

    # New:
    timeline = boundaries.from_media(media_obj, "scene", chunk_s=20.0)

    # The new method returns the typed result object directly.
    # It does NOT write to disk by default. Accept an optional sink= to
    # opt into writing.

Component-by-component:

    media       Already has split() which does the work without writing.
                No change needed. split() is the model for the others.

    audio       Add: audio.from_media(media: Media, ...) -> RawTranscript
                Accepts a Media object instead of resolving media.json by id.

    boundaries  Add: boundaries.from_media(media: Media, policy, ...) -> Timeline
                For scene/vad/speaker, also accept cuts data:
                boundaries.from_evidence(media: Media, cuts: Cuts, ...) -> Timeline
                evidence() similarly: boundaries.evidence_from_media(media, ...) -> Cuts

    video       Add: video.from_inputs(media: Media, timeline: Timeline, ...) -> Manifest
                Must also accept a frame source (path or readable stream)
                since it needs to decode frames.

    cut         Add: cut.from_inputs(timeline: Timeline, raw: RawTranscript) -> Transcript

    describe    Add: describe.from_inputs(manifest: Manifest, timeline: Timeline,
                    frames: dict[str, bytes | Path], ...) -> Descriptions
                frames maps frame filenames to their content or paths.

    embed       Add: embed.from_inputs(descriptions: Descriptions,
                    transcript: Transcript | None, ...) -> EmbeddedDocuments
                This one is trickier because it writes to an external index.
                The return value should carry the texts and metadata; writing
                to the index stays opt-in via index_name=.

    retrieve    Already takes a query, not an id. No change needed.

Rules for the new methods:
- They return the typed result object, not Produced.
- They do not read from or write to disk unless sink= is passed.
- They validate inputs the same way run() does (refuse unknown settings, etc).
- They do not require configure() to have been called.
- They share the same core logic as run(). Factor the work out of run() into
  an internal function, and have both run() and from_*() call it.

Testing: each new method should be callable with no filesystem setup. Write
tests that construct input objects in memory and pass them through.


2. DOCUMENT ALL PUBLIC TYPES
============================

Goal: every type the library returns should be fully documented with its
fields, their types, and what they mean.

Types to document (add docstrings and a TYPES section to the library docs):

    Media
        video_id: str
        path: Path                  # original file location
        duration_s: float
        has_video: bool
        has_audio: bool
        streams: list[StreamInfo]   # codec, resolution, etc.
        fingerprint: str            # content hash for re-run detection
        (list all fields; adjust names to match actual code)

    RawTranscript
        video_id: str
        language: str | None
        words: list[Word]           # document Word: text, start, end, speaker, confidence
        segments: list[Segment]     # document Segment
        turns: list[Turn]           # document Turn
        (no chunk ids -- that is cut's job)

    Cuts
        video_id: str
        policy: str
        scores: list[float] | None  # the raw score series, if scene
        cut_points: list[float]     # timestamps where cuts fall
        (whatever the actual structure is)

    Timeline
        video_id: str
        policy: str
        chunks: list[Chunk]         # document Chunk: id, start_s, end_s
        duration_s: float

    Manifest
        video_id: str
        frames: list[FrameRecord]   # document FrameRecord: chunk_id, timestamp,
                                    #   sampler, question, path_in_store
        sampler_specs: list[str]    # the parsed sampler strings

    Transcript
        video_id: str
        chunks: dict[str, ChunkTranscript]  # chunk_id -> words/text for that chunk

    Descriptions
        video_id: str
        entries: list[Description]  # document Description: chunk_id, sampler_id,
                                    #   question, content, describer, prompt_hash

    EmbeddedDocuments
        (whatever embed.readable() returns -- document it)

    Produced
        video_id: str
        component: str
        artifacts: dict[str, Path]  # artifact name -> file path
        stats: dict[str, Any]       # headline numbers (e.g. has_audio, chunk_count)
        skipped: list[str] | None

    Run
        video_id: str
        steps: list[Produced]
        skipped: dict[str, str]     # component -> reason

    Moment
        video_id: str
        chunk_id: str
        start_ts: float
        end_ts: float
        score: float                # rank fusion score, not similarity
        hits: list[Hit]

    Hit
        sampler_id: str
        sampler: str
        question: str | None
        content: str
        structured: dict | None
        dense_rank: int
        text_rank: int | None       # None = lexical half silent

Adjust all field names and types to match the actual code. The point is:
every field a user might access should be documented.

Implementation: add these as docstrings on the classes, and generate a
TYPES.md or a "Types reference" section in the main docs from them.


3. SESSION / WORKSPACE CONTEXT OBJECT
======================================

Goal: replace the global falconvar.configure() with an explicit context
that carries config and can be passed through calls. Keep the global
configure() as sugar for the common single-pipeline case.

    class Workspace:
        def __init__(self, data_root=None, env_file=None):
            # Resolution order for data_root:
            #   1. explicit argument
            #   2. $FALCONVAR_DATA
            #   3. checkout directory
            #   4. ~/.falconvar

        # Every Level 1 component is available as a method or attribute:
        #   ws.media.run("talk.mp4")
        #   ws.boundaries.run(vid, "scene")
        # These behave identically to the module-level calls but use
        # this workspace's config.

    # The global configure() sets a default workspace used by the
    # module-level calls:
    def configure(data_root=None):
        _default_workspace = Workspace(data_root=data_root)

Two workspaces in the same process must not interfere. Each workspace
resolves paths relative to its own data_root. No module-level mutable
state beyond the single _default_workspace reference.

API key handling stays the same (env vars / .env file). The Workspace
can accept an env_file= path for cases where two workspaces need
different keys.


4. ASYNC INTERFACE
==================

Goal: provide async versions of every component's run() and the new
from_*() methods. I/O-bound stages (describe, embed, audio) benefit
most, but offer async across the board for consistency.

Approach:
- Add async variants: audio.arun(), describe.arun(), embed.arun(), etc.
  Or if the codebase is already async-friendly internally, make run()
  async and provide a sync wrapper.
- For describe, support concurrent API calls within a single run:
  add a concurrency= parameter (default 1 for backward compat) that
  controls how many chunk descriptions are in flight at once.
- For embed, the batch= parameter already batches texts; make the
  API calls within a batch concurrent.
- For video (frame decoding), async may not help (CPU-bound), but
  the method should still be awaitable so callers can run multiple
  videos concurrently with asyncio.gather().

Pick one of these shapes (whichever fits the existing code better):

    # Option A: separate async methods
    produced = await describe.arun(vid, describer="openai", concurrency=4)

    # Option B: run() is async, sync wrapper provided
    produced = await describe.run(vid, describer="openai", concurrency=4)
    produced = describe.run_sync(vid, describer="openai")  # blocking


5. FINE-GRAINED PROGRESS REPORTING
===================================

Goal: let callers observe and react to progress within a component,
not just before/after the whole component.

Changes:

a) Add an on_progress callback to describe.run() and embed.run():

    def on_progress(event: ProgressEvent):
        ...

    describe.run(vid, describer="openai", on_progress=on_progress)

    ProgressEvent:
        component: str          # "describe"
        total: int              # total units to process
        completed: int          # units done so far
        skipped: int            # units skipped (already described)
        current: str | None     # e.g. "chunk_003:clip:text"
        result: Any | None      # the unit's result, if completed

b) As an alternative to callbacks, support an iterator/generator mode:

    for event in describe.iter(vid, describer="openai"):
        print(f"{event.completed}/{event.total}")
        if event.completed > budget:
            break  # stopping mid-run is safe; resume=True picks up later

c) Level 2: extend on_step to carry progress events from the current
   component:

    def on_step(component, result, progress=None):
        if progress:
            print(f"  {progress.completed}/{progress.total}")


6. FORMAL SAMPLER SPEC GRAMMAR
===============================

Goal: document the sampler spec mini-DSL with a clear grammar so users
know exactly what is legal.

Write a SAMPLER_SPEC section in the docs (and as a module docstring on
whatever parses these) with:

    Grammar (informal BNF):

        spec_list   = spec ("," spec)*
        spec        = sampler_name (":" question)?
        question    = plain_text | "[" question_list "]"
        question_list = plain_text ("," plain_text)*
        sampler_name  = "clip" | "yolo" | "objects" | "text" | "uniform"
        plain_text    = <any characters except , [ ] : (unescaped)>

    Escaping: to include a literal comma, colon, or bracket in a
    question, use backslash: \, \: \[ \]

    Merging: if the same sampler_name appears more than once in a
    spec_list, the questions are merged into one run of that sampler.
    "clip:text,clip:scene" is equivalent to "clip:[text,scene]".

    Examples:
        "uniform"                     uniform sampler, no question
        "clip:text"                   clip sampler, question "text"
        "clip:[text,scene]"           clip sampler, two questions
        "clip:text,yolo"              clip with question, yolo without
        "clip:text,clip:scene,yolo"   same as "clip:[text,scene],yolo"

    Invalid (and the error you get):
        "clip:[text"                  unmatched bracket
        "unknown:text"                unknown sampler name
        "clip:text,clip:text"         duplicate question (warn or dedup?)

Also: add a parse_sampler_spec() function to the public API so users
can validate a spec string before passing it to run().

    from falconvar.video_rag import parse_sampler_spec
    specs = parse_sampler_spec("clip:[text,scene],yolo")
    # Returns a list of (sampler_name, list[question]) tuples


7. SINK DOCUMENTATION AND VALIDATION
=====================================

Goal: centralize what sink= means, which sinks exist, and which
components support which sinks.

Add a SINKS section to the docs:

    Available sinks:
        file       write to the output directory (<data>/out/<video_id>/)
        supabase   write to a Supabase project (needs SUPABASE_URL and
                   SUPABASE_KEY in environment)

    Per-component support:
        media       file | supabase
        audio       file | supabase
        boundaries  file | supabase    (both evidence and run)
        video       file               (supabase not supported: frames are local)
        cut         file | supabase
        describe    file | supabase
        embed       N/A (uses index_name instead)
        retrieve    N/A (reads from index)

    Multiple sinks: "file,supabase" writes to both, in order. A failure
    in the second sink does not roll back the first.

    If a component does not support a requested sink, it raises
    FalconvarError at call time, not after doing the work.

Adjust the table above to match reality. The point is: a user should
be able to look up what sink= does for any component without guessing.


8. STRUCTURED LOGGING AND OBSERVABILITY
========================================

Goal: every component should emit structured log records so users can
debug pipeline runs, measure timing, and trace what was read/written/
skipped.

Implementation:

a) Use Python's logging module with a named logger per component:

    logger = logging.getLogger("falconvar.describe")

b) Log at these levels:
    DEBUG    what was read, what was skipped, per-unit timing
    INFO     component started, component finished, headline stats
    WARNING  a setting was resolved by fallback (e.g. embedder defaulted
             to openai because $FALCONVAR_EMBEDDER was not set)
    ERROR    a unit failed but the run continued (if that ever happens)

c) Each log record should include structured fields (use logging's
   extra= or a custom formatter):
    - video_id
    - component
    - event (e.g. "read", "write", "skip", "call", "done")
    - duration_ms (for timed events)
    - artifact (for read/write events)
    - reason (for skip events)

d) By default, falconvar configures NO handlers on its loggers (library
   best practice). Users attach their own:

    import logging
    logging.getLogger("falconvar").setLevel(logging.DEBUG)
    logging.getLogger("falconvar").addHandler(logging.StreamHandler())

e) Level 2 (video_rag) should log the full pipeline timing:

    INFO  video_rag started video_id=talk policy=scene
    INFO  media finished video_id=talk duration_ms=120
    INFO  audio finished video_id=talk duration_ms=8400
    ...
    INFO  video_rag finished video_id=talk total_ms=34200 steps=8 skipped=0


9. COMMON SEARCH PATTERNS IN DOCS
===================================

Goal: add a "Common patterns" section to the retrieve.search docs
showing the 4-5 most common ways to call search, so users don't have
to puzzle over the full parameter list.

    COMMON SEARCH PATTERNS
    ----------------------

    # Search all videos for a moment:
    moments, notes = retrieve.search("the audience laughed")

    # Search one video:
    moments, notes = retrieve.search("the audience laughed", video_id="talk")

    # Search by time range within a video (seconds):
    moments, notes = retrieve.search("key insight", video_id="talk",
                                      after=120.0, before=300.0)

    # Search only clip-sampled content with a specific question:
    moments, notes = retrieve.search("diagram of the architecture",
                                      video_id="talk", question="text")

    # Search multiple specific videos:
    moments, notes = retrieve.search("budget discussion",
                                      video_ids=["q1_review", "q2_review"])

    # Always read the notes when moments is empty:
    moments, notes = retrieve.search("something very specific", video_id="talk")
    if not moments:
        print("No results:", notes)


IMPLEMENTATION ORDER
====================

Suggested order, based on dependencies and impact:

    1. Document all public types (#2)
       No code changes, unblocks everything else.

    2. Formal sampler spec grammar (#6)
       Small scope, self-contained, improves validation.

    3. Sink documentation (#7)
       No code changes, clarifies existing behavior.

    4. Common search patterns (#9)
       No code changes, documentation only.

    5. Structured logging (#8)
       Touches every component but is additive (no breaking changes).

    6. Dual-mode component interface (#1)
       The largest change. Factor internals first, then add from_*().

    7. Session/Workspace context (#3)
       Depends on understanding all the global state, easier after #1.

    8. Fine-grained progress (#5)
       Easier to add after the internals are factored (#1).

    9. Async interface (#4)
       Easiest to add last, once the sync internals are clean.
